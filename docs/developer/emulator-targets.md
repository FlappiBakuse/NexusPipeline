# Emulator targets

`POST /control/v1/automation/emulators/discover`, CLI `control emulator-discover --input <file>` and MCP `emulator_discover` use the installed EmulatorSupport provider. The request is `control-emulator-discover.schema.json`: a saved script, exact catalog revision and up to 32 declared search roots. Windows uninstall registry locations supplement portable roots. Discovery executes only the provider's fixed read-only enumeration commands and returns bounded selectors and diagnostics; it does not start a VM. The Web Android target editor stores an explicit instance, endpoint and bundled ADB choice in its ordinary automation draft. Newly discovered roots use the existing automation change transaction when the draft is saved.

Generic scripts retain Android support. Specialized scripts require an enabled, published and installed manifest with `target.android`. BAAH, MaaEnd and MaaStellaSora declare that capability. A request flag, PID, window or display name cannot grant it. Provider installation revision, package hash and activation, physical control/ADB images, the VM directory identity, vendor selector and source evidence enter the execution plan. LDPlayer uses an existing `vms/leidian<index>` directory; Nox requires the matching VM configuration directory; BlueStacks uses the selected `Engine/<instance>` directory. Missing or ambiguous directories are refused.

Generation follows the physical VM directory and stable vendor selector. Ordinary atomic configuration updates do not create a new generation. Each Android command start and media read re-enters the installed provider to verify the current mapping and generation. Discovery leases end before vendor launch or ADB operations, so a vendor can write its runtime configuration. Only immutable execution images and the selected directory identity remain held by the plan.

The existing Android command owner derives vendor launch/quit arguments and ADB application/readiness/media operations from the frozen source. BlueStacks can produce `OwnedHandoff` only from an actually started, still living registered Job root. Its engine fact remains `Unknown`; ADB foreground readiness is separate. A vendor launch family remains owned through main collection and cleanup. Shutdown requires the existing explicit final cleanup decision and independent offline observations. When the VM is retained, the original owner publishes a retention intent before changing Job lifetime flags, verifies the native handoff, and records that family in the Android collection. A partial or unverified handoff remains unresolved for recovery.

Controlled process fixtures exercise these owners with the original EmulatorSupport ZIP. They do not qualify an installed LDPlayer, Nox or BlueStacks release. All three real-vendor qualifications remain `NOT_RUN` until corresponding installations are available.
