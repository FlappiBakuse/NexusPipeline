# 长期恢复容量的限定修复

恢复容量区分活动家族和完成历史。活动容量上限仍为 10,000 个 journal、65,536 个文件 effect、10,000 条 Job 成员记录；完成历史保留完整证据，不永久占用新工作额度。

已实现的读取和预算语义如下。

1. 预留额度保护活动家族及仍有待清理 effect 的家族，不再统计完全结束且无需后续写入的历史家族。维护回滚及重启余量在真实后继启动交接结束前保留。
2. 恢复批次仅装载活动家族；按 journal 读取的历史事实改用现有索引点查，涉及配置父子关系时读取同一家族。用于证明隔离完整性的全局检查仍针对完整活动集合，不能拿单个家族快照替代。
3. 冷启动、秘密及 blob 引用清单仍访问完成历史，按主键分页读取并逐项进行原有类型、摘要、writer、SQL/物理一致性校验。不能把不在活动批次误判为不存在或无引用。
4. 不删除历史证据，不提高活动恢复上限，不新增数据库、journal 格式、缓存或第二套恢复权威。日志/图片保留另用既有精确清理流程。

涉及 owner 为 RecoveryCapacityStore、RecoveryCapacityInventory、RecoveryJournalRegistry 及 StartupJournalRecovery。其调用方按点查、同家族校验、全局活动校验、历史引用四类逐一核对；禁止用批量正则替换迁移语义。

最小验证出口：超过旧全局历史阈值后可继续受理；新的活动额度仍拒绝超额；未完成家族和回滚余量不被抢占；历史引用继续阻止删除；旧历史篡改仍拒绝启动；代表执行、冷恢复及维护重启保持有效。只补这些变化影响的定向证据，不重跑无依据全量。

完成历史、预算、writer 停止证明、取消父绑定和维护元数据使用有序分页读取；每页继续调用原有 typed 校验。点查只服务已绑定的 journal/operation，家族快照不能替代全局活动隔离检查。公开诊断快照仍有原有限上限，不作为生产历史读取入口。

`p1-history-paging-r01` 的四个定向方法通过：10,001 条完成恢复元数据及维护元数据跨过旧上限；真实停止证明和取消记录按单项分页仍拒绝末页篡改；真实完成 journal 篡改在冷恢复写入前拒绝；真实维护交接完成。大数据用例仅证明 SQL 计数与读取语义，不冒充 10,001 次原生执行或完整 Host 启动性能。活动各维容量、冻结预算、未完成家族、配置恢复、重试和回滚另由本轮有限组件及真实链路报告覆盖，详见业务保留文档。
