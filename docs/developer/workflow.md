# 先完成代码，再统一定向验证

本流程适用于本次开发包选定的任务集合。默认选定范围跨 Host 与 Plugins，必须先集中完成代码、必要的产品断言及文档，再进入统一验证。每个任务卡的“完成”不触发一次独立全套验证。

## 1. 只做必要准备

核对两个实际仓库的分支、HEAD、工作区与暂存区；识别现有用户修改，只检查所选任务相关漂移。不要 reset、clean、自动 stash 或用参考提交覆盖本机工作。

只检查选定任务需要的工具和输入是否具备。版本读取、文件阅读、diff 和任务映射属于准备；不在这个阶段跑基线全量测试、性能压力、生产构建或真实游戏来“了解项目”。

阅读根 AGENTS、对应任务卡和 [Agent 任务地图](../agents/change-map.md)中指向的最少文档。用户这次对产品语义和验证范围的要求优先于旧阶段材料；不能因为旧登记系统要求数量对账而扩大本次产品测试。

## 2. 冻结任务范围与产品假设

为选定任务记录：恢复的可观察行为、代码 owner、允许修改的边界、完成条件和统一验证中要证明的反例。main 用于行为 oracle，next 用于当前架构、协议和风格。

默认完成开发包选定的全部代码卡后再验证。依赖关系决定实现顺序，不把每张卡拆成“实现→全测→下一卡”。有条件诊断卡先完成最小诊断支持，统一观察阶段取得真实证据后，只补证据指向的代码差异。

没有调用者、真实输入或已证故障支撑，不加入兼容分支、通用缓存、第二套恢复机制或额外平台支持。已有代码只因本卡行为需要才改动；目录比例、总行数和覆盖率不是扩大任务的理由。

## 3. 集中实现

按依赖顺序完成 Host 与插件代码。共用 schema/SDK 真有变化时先改唯一权威并生成必要源文件，随后更新实际消费者；只有 Host 内部策略变化时不强迫插件升级协议。

同阶段调整需要保留的产品断言，删除或迁出纯实现锁定，更新实际受影响的用户步骤与开发规则。允许阅读和审查 diff；此时不执行 lint、typecheck、test、build、benchmark 或浏览器回归。

生成代码属于实现输入，不属于业务 PASS。生成器输出需要纳入最终源身份，不能在验证中悄悄修改产品源码。不要为一次小改把全部测试改写到新框架。

## 4. 关闭代码批次

进入统一验证前确认：

- 选定代码卡已实现；诊断条件卡的可执行观察点已就绪。未完成代码或真实阻塞单列，不能记作代码完成，也不能作为提前跑其余全套验证的理由。
- 两仓需要的契约和消费者已经对应，文档里的目标与实际实现一致。
- 受影响断言已选定，每条都有产品假设和最小证明层；重复命令和重复场景已经合并。
- 构建槽、隔离实例、浏览器及必要原包输入指向确定路径；用户真实运行目录不作夹具。

这里是工作状态转换，不要求再次向用户申请已经授权的实现许可。源码可以未提交；“冻结”指本轮测试与产物绑定的明确字节集合，不是强制 git commit。

## 5. 执行一次统一的定向计划

按 [验证规范](validation.md)分别记录 lint、typecheck、test、build。测试需要二进制或浏览器依赖时，先准备实际所需闭包；准备步骤与测试结果分列，不能为了形式顺序重复编译。

同一规则在最低有效层已充分证明，就不再给每个入口重复写一套实现镜像测试。实际跨边界风险用最小组合场景补足。只有任务影响共享 ABI、真实原生入口或恢复事实时，才扩大到对应消费者或原生层。

## 6. 失败后只补受影响范围

保留首个失败的原始输出，定位根因。产品代码失败回到实现阶段修复；工具或夹具失败先区分其与产品结论。修复后记录新的输入身份，只重跑失败项和由该次改动实际影响的依赖项。

修了一个解析错误不自动重跑全仓；变更了公共契约也不能只重跑一个无关纯函数。扩大范围必须写出具体传播链。不要无条件重试、删断言、改阈值或复用旧 PASS 掩盖失败。

## 7. 交接与文档微调

交付改动摘要、真实产物或其明确阻塞、实际验证结果、未运行项和剩余问题。只有实际受影响的说明需要微调；实现后的目标稿去除已过期的临时步骤，并更新状态行，不重写整套文档。

源码与产物身份、原始结果和必要诊断保留到交付结束。没有真实 Windows 运行就写 NOT_RUN；没有正式发布就不把本地安装成功写成已上线。新的提交和远端操作继续按已授予权限执行。

现役源码快照包括仓内文档。业务说明尽量在代码阶段定稿，PASS和原始验证结果默认写仓外。验证后确需纯文档微调时，记录docs-only delta，明确已构建产物的冻结输入与当前工作树的区别；不能宣称旧receipt覆盖新全树。只补这份文档的必要检查，不无故重跑产品。若交付约束要求包含新文档的产物，再做最小产物准备，不放宽来源校验。
